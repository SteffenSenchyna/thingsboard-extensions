# Device Emulator Generator (per-profile worker)

Goal: for **one** device profile, generate complete emulator task files for every device of that profile. The worker handles all three stages (strategy selection → full strategy JSON → save) end to end. Different profiles' workers run in parallel under the `generate-emulators` skill.

The save step (`tb emulator add`) writes one task file per device under `solutions/<solution>/tasks/emulators/<device-uuid>.json` — different files per call, so saves dispatch in **parallel batches** within this worker as well.

## Demo data cadence — fixed assumption

Every emulator generated by this worker produces telemetry on the **same fixed schedule**:

- **Window: 7 days** — always pass `--days 7` to `tb emulator add`. Do not shorten and do not extend.
- **Tick interval: 30 minutes** — the emulator emits one sample per key per 30-minute tick. That is **48 ticks/day**, **336 ticks/week**.
- All `anomalyChance` / `minIncrement` / `minDecrement` / `INCREMENT` / `DECREMENT` / `COUNTER` rate values must be sized to this cadence (per-tick = per-30-min). If the briefing materials quote real-world frequencies (e.g. "twice a day"), convert with `anomalyChance = 48 ÷ fires_per_day`.
- This cadence is shared with the calculated-fields pipeline — see `cf-generator.md` "Telemetry cadence" for the matching CF assumptions (45-min `timeWindow` on `TS_ROLLING`, `HOUR`/`DAY` aggregation intervals, etc.).

## EXTREMELY IMPORTANT — anti-shortcut rules

- Never write phrases like "due to time/complexity constraints," "for brevity," "to wrap up," "let me create a simplified version," or any synonym.
- Generate emulator task files for **exactly** the devices in the brief's `devices` array. No "representative sample," no skipping.
- For every telemetry key in the profile **that survives the CF-output filter in Step 1**, pick a strategy and generate a complete strategy JSON. Do not omit surviving keys to save tokens.
- **Never use `CONSTANT` for a cumulative counter.** Keys that semantically represent monotonically growing totals — name suffixes like `Count`, `Counter`, `Total`, `Sum`, `Runs`, `Cycles`; energy / water / distance / fuel accumulators; transaction counts; uptime hours — MUST use `COUNTER` (positive `minIncrement` / `maxIncrement` per 30-min tick, with a far-future reset bound). `CONSTANT` flatlines the counter, so dashboards show no change, `delta` CFs that read it always produce zero, and the user sees a dead system. The only legitimate `CONSTANT` use cases are listed in the CONSTANT section below — none of them are counters.
- If any `tb emulator add` call errors, finish in-flight results in the current batch, then stop and surface the error verbatim.

## Brief inputs

- `solution` — solution slug.
- `profile` — name of the device profile this worker handles.
- `devices` — JSON array of `{id, name}` for every device of this profile (already discovered by the skill from `solutions/<solution>/devices/*.json`).
- `architectureOverviewPath` — absolute path to `architecture-overview.md`, the single design artifact. Source of the profile's keys, the parent chain, alarm thresholds, the derived-key exclusion, and GPS/User-Requirements context.

## Step 1 — Load context

In a single parallel batch:

1. `Read` `<architectureOverviewPath>`.
2. `Read` `@/Users/steffensenchyna/.thingsboard/resources/prompts/solutions/data-generator/resources/generator-guidelines.md` — strategy selection rules and per-strategy ctx reference.

Extract from the overview's `### <profile> (DEVICE)` subsection:
- The profile's keys from its `Telemetry:` sub-list, with `dataType`, min/max, and enum values as stated.
- Confirm the profile exists. If not, stop with `error: profile '<profile>' not found in architecture-overview.md`.
- **Exclude derived keys.** Any `Telemetry:` key annotated `(derived: <CFName>)` is a calculated-field output — the CF system computes it, so emitting an emulator entry for it double-writes and breaks reprocess. **Remove every `(derived: …)`-annotated key from the profile's key list before Stage 1.** (Derived keys can also land on other profiles via `propagate`/`related-aggregation`; the annotation marks them wherever they appear.)

Extract from the overview's `## Relations`: the parent zone/asset chain for this profile (the prose links where this profile is the child).

Extract from the overview's `## Alarms`: every alarm bullet that references a key of this profile — extract threshold values.

Extract from the overview's "Customers & Users" and "Summary" sections for customer name + site context for GPS anchoring. **Also parse the `## User Requirements` section** — every bullet whose **Affects** mentions emulator tick, telemetry interval, demo data span, or value bounds for keys on this profile is a HIGH-PRIORITY override:
- **Telemetry interval** (e.g. `AirQualitySensor.aqi: 10 min`) — set the emulator's per-key tick to that interval (overrides the default 30-min cadence used by `COUNTER` increments, `NATURAL` walks, etc.). For numeric strategies, scale `minIncrement`/`maxIncrement` and any decay/growth ctx phrasing to the new tick so the per-hour rate the user expects is preserved.
- **Demo data span** (e.g. `30 days of history`) — set the brief's `days` parameter pass-through accordingly when the brief left it at the default.
- **Value bounds / expected range** (e.g. `aqi between 20 and 200 typical`) — clamp `minLowValue`/`maxHighValue` in the strategy so emulated values stay within the user's range, even if the profile's `minValue`/`maxValue` is broader.
If no such requirement applies to this profile, defaults run unchanged.

`TodoWrite` one todo per device in the brief's `devices` array. Mark each `in_progress` at Step 3 start, `completed` on save success.

## Step 2 — Stage 1 (overview) and Stage 2 (full strategy JSON)

### Stage 1 — Strategy selection per key (once per profile)

For each telemetry key in the profile, apply `generator-guidelines.md` rules to select:

- `valueStrategyType` — boolean → COMPOSITE/EVENT/CONSTANT only; string/enum → CONSTANT/SEQUENCE only; double/integer → any numeric strategy.
- `ctx` — concrete behavioral sentence per the per-strategy ctx reference in the guidelines.

**Note on SEQUENCE keys.** GPS keys (latitude/longitude) and indoor position keys (xPos/yPos, and similar spatial keys) must NOT be added to the profile-level `keys[]` array. They run **per device** so each device gets unique coordinates. Mark them in a `sequenceKeyOverrides` map keyed by device id.

**Alarm-demo assignment (from generator-guidelines.md §4):**

Count devices of this profile: `N = len(devices)`. Alarm-demo count: `max(1, round(0.25 × N))`.

For each alarm that references a key in this profile:
- Pick `max(1, round(0.25 × N))` devices as alarm-demo for that alarm (different alarms can share devices).
- Alarm-demo devices: set `valueStrategyType=CONSTANT`, `ctx="Fixed at <value> to trigger <AlarmName> in demo"`.
- Normal devices: pick a safe oscillating strategy per the alarm-demo guidance in `generator-guidelines.md` §4.

If no alarms reference any key of this profile, skip alarm-demo assignment entirely — all devices use the standard strategy selection.

**SEQUENCE keys (GPS / indoor position):**
- Run per-device — each device needs unique coordinates.
- GPS: anchor to customer name; generate coordinates inside the parent zone's perimeter. **Use the same geographic anchor the attribute generator uses for area polygons** — priority: (1) a city/region named in the architecture-overview/customer context; else (2) the **canonical default `37.7749, -122.4194` (San Francisco)**. Never default GPS to a different region than the area polygons (e.g. NY vs SF) — markers must land in the same region as, and inside the footprint of, their parent area's polygon, or the map shows markers and polygons in different places (or nothing in view).
- Indoor (xPos/yPos): compute a grid layout within [0.0, 1.0]; embed the exact coordinate value in `ctx` so Stage 2 uses it verbatim.
- See guidelines §4 "Indoor Position Uniqueness" for the grid pattern.

**Stage 1 in-memory output:**

```
{
  "keys": [{"key": str, "valueStrategyType": str, "ctx": str, "dataType": str}, ...],
  "devices": [
    {"id": str, "name": str,
     "sequenceKeyOverrides": {"<key>": {"valueStrategyType": "SEQUENCE", "ctx": str}}
    }, ...
  ]
}
```

`sequenceKeyOverrides` is populated only for GPS/indoor keys; it replaces the profile-level entry for that specific device.

### Stage 2 — Full strategy JSON

For each `(key, valueStrategyType, ctx, dataType)` from Stage 1:

- **Non-SEQUENCE keys:** iterate the profile-level keys — generate once per profile, cache by `key`.
- **SEQUENCE keys:** iterate each device's `sequenceKeyOverrides` entries — generate once per device per key, cache by `(deviceId, key)`.

For each strategy, follow the per-type rules. Output must be **minified JSON** conforming to the schema for the chosen strategy type.

**Per-strategy rules** (reference `@/Users/steffensenchyna/.thingsboard/resources/prompts/solutions/data-generator/resources/value-strategies/<lowercase-type>-value-strategy-schema.json` and `…-value-strategy-example.json`):

#### NATURAL — fluctuating numeric values (temperature, humidity, pressure, CO₂, etc.)
- `type: "NATURAL"`, 0–2 decimal places per metric.
- `minLowValue`/`maxLowValue`: lower threshold range before increasing; `minHighValue`/`maxHighValue`: upper threshold before decreasing.
- `minIncrement`/`maxIncrement` and `minDecrement`/`maxDecrement` control rate of change.
- Multipliers (`holiday`, `workHours`, `nightHours`) shape daily/weekly patterns.
- `decrementOnStart: false` unless ctx says otherwise.
- If ctx mentions alarm thresholds (e.g. "alarm < 90 or > 95"), set oscillation bounds slightly outside each threshold so the value naturally dips/spikes across them (e.g. low 87–89, high 96–99).
- Reference ranges: Temperature 10–35°C slow, Humidity 30–80% medium, Pressure 980–1020 hPa very slow, CO₂ 400–2000 ppm medium.

#### COUNTER — continuously increasing values with reset (energy kWh, water L, odometer km)
- `type: "COUNTER"`, 0–2 decimal places.
- `minStartValue`/`maxStartValue`: range after reset; `minEndValue`/`maxEndValue`: range before reset (large).
- `minIncrement`/`maxIncrement`: rate per 30-minute tick.
- Multipliers: `workHoursMultiplier > 1.0` for accumulating-faster-during-work-hours keys.
- Reference ranges: energy 0–1000 → ~10M; water 0–100 → ~1M; odometer 0–10000 → ~500000.

#### EVENT — binary toggle (motion/door/alarm/leak — boolean only)
- `type: "EVENT"`, `normalValue: false`, `anomalyValue: true`.
- `anomalyChance` per 30-min tick (336 ticks/week): ~10/day → 5; ~5/day → 10; ~2–3/day → 16–24; once/day → 48; every 2–3d → 100–150; once/week → 336.
- Never use vague words like "rare" — always a concrete number derived from ctx frequency.

#### CONSTANT — fixed value (firmware version, hardware version, device type, enabled flag, alarm-demo fixed value)
- `type: "CONSTANT"`. Use correct literal: boolean → true/false; numeric → number; string/enum → string literal.
- For enum dataType, pick one value from the enum list in ctx.
- If ctx specifies a concrete value ("Fixed at 8% to trigger LowFuel"), use exactly that.

#### SEQUENCE — predefined value list, sequential or random (GPS, indoor positioning, enum cycles)
- `type: "SEQUENCE"`, `random: false` for sequential / `true` for random.
- `telemetry` object: key → array of values; all arrays must have the same length.
- For enum dataType: values must be string literals from the enum list — never numbers.
- For GPS (lat/lng): if ctx contains perimeter bounds, generate 5–10 realistic waypoints inside/near the perimeter — no random jumps.
- For indoor (xPos/yPos): if ctx contains an exact coordinate (grid pattern), use that as a CONSTANT array (all elements identical); otherwise generate a path inside [0.0, 1.0].

#### COMPOSITE — day-vs-night EVENT mix (motion sensors, parking occupancy, presence — boolean only)
- `type: "COMPOSITE"`. Two required sub-strategies: `defaultHours` (lower anomalyChance, more frequent) and `nightHours` (higher anomalyChance, less frequent). Both follow EVENT rules.
- Pick anomalyChance values that reflect the daytime/nighttime contrast (e.g. 30 day vs 500 night).

#### SCHEDULE — time-of-day INCREMENT/DECREMENT switching (occupancy ramps, HVAC, parking — numeric only)
- `type: "SCHEDULE"`. **Never use SCHEDULE for boolean keys.**
- `timeZone` from customer context or `"UTC"`.
- `schedule` array: 2–4 non-overlapping windows per day. Each entry `{startHour, startMinute, endHour, endMinute, definition: {type: "INCREMENT"|"DECREMENT", ...}}`.
- `defaultDefinition`: used outside scheduled windows — typically DECREMENT or low-activity INCREMENT.
- Typical patterns: morning 6–9am INCREMENT (ramp-up), evening 17–20pm DECREMENT (ramp-down).

#### INCREMENT — steady increase from startValue to endValue then stop (tank filling, battery charging, capacity filling)
- `type: "INCREMENT"`, 0–2 decimal places.
- `minStartValue`/`maxStartValue` lower; `minEndValue`/`maxEndValue` higher; `endValue > startValue`.
- `minIncrement`/`maxIncrement` per 30-min tick — pick so the range fills over several days, not hours.
- Reference: tank 20→100%, battery 20→100%, occupancy 0→max capacity.

#### DECREMENT — steady decrease from startValue to endValue then stop (battery drain, fuel consumption, cooldown)
- `type: "DECREMENT"`, 0–2 decimal places.
- `minStartValue`/`maxStartValue` higher; `minEndValue`/`maxEndValue` lower; `endValue < startValue`.
- `minDecrement`/`maxDecrement` per 30-min tick — pick so drain takes several days, not hours.
- Reference: battery 70→20%, fuel 80→10%, temperature 80°C → ambient.

**Stage 2 in-memory output:** a cache of full strategy JSON keyed by `key` (non-SEQUENCE) or `(deviceId, key)` (SEQUENCE).

## Step 3 — Save emulators in parallel batches

For every device in the brief's `devices` array, assemble its `telemetryProfiles` array:
- For every non-SEQUENCE key in the profile's Stage 1 overview: use the cached Stage 2 JSON for that key.
- For every SEQUENCE override on this device: use the per-device cached Stage 2 JSON for `(deviceId, key)`.

Each device's final task JSON shape: `{"telemetryProfiles": [{"key": "<key>", "valueStrategy": <full-strategy-json>}, ...]}`.

Each call writes to `solutions/<solution>/tasks/emulators/<device-uuid>.json` — different files, so dispatch saves in **parallel batches of up to 10 `tb emulator add` calls per message**. Wait for each batch to return before sending the next; stop on any error.

```bash
tb emulator add \
  --entity-type DEVICE \
  --entity-id <device-uuid> \
  --solution <solution> \
  --days 7 \
  --json '{"telemetryProfiles": [<assembled-array>]}'
```

On success per device: mark its todo `completed`. On failure: keep the todo `in_progress`, record `ERROR — <tb error message>`, surface the error and stop the batch.

## Step 4 — Return value

Print one line per device, then a totals line:

```
device <uuid> (<name>): <N> keys emulated  [profile: <profile-name>]
device <uuid> (<name>): ERROR — <tb error message>
profile <profile>: <D> devices, <K> total key assignments, <E> errors
```

The skill aggregates one of these blocks per profile.
